# Passphrase and locked state

- The app starts locked. The tray icon shows a lock glyph. No file is read until unlock.
- Unlock is prompted at launch. If dismissed, the app stays in the tray locked, and the next hotkey press prompts for the passphrase before showing the capture box. The prompt shows the data file's path under its heading, so it is clear which log is being unlocked.
- After unlock, the data key stays in process memory until the app exits or is locked, by Lock now, by idle auto-lock or by a workstation lock.
- Idle auto-lock takes the Lock now path below after `idleLockMinutes` ([settings.md](settings.md)) without input, and the next hotkey takes the same "prompt first, then capture" path. "Without input" means no keyboard or mouse input to the Windows session at all (`GetLastInputInfo`), not just to Logbook: the point is that you walked away from the machine, and locking while you work in other apps would make every capture ask for the passphrase and kill the habit the app exists for. It is checked once a minute while unlocked and the check stops on lock; due means at least N minutes since the last input, and a last input that appears to lie in the future (a clock change) is not idle. A check never shows a dialog: while anything is pending or being written it skips and tries again next minute, since the tray icon already shows the pending count, and while one of the app's modal dialogs is open it waits too, so a half-made decision there is not closed under you, though not forever: once twice the idle limit has passed without input it locks anyway and the dialog closes with it. Otherwise it closes what Lock now closes, so a capture box with typed text and an unsaved edit in the detail pane are lost, which is "clear the data key after N minutes" taken literally.
- "Lock now" in the tray menu returns to the startup state: the open log (data key and decrypted entries) is dropped and the data key zeroed in memory, every window that shows entries closes (the toasts too, since the "Logged" toast shows a summary), the lock glyph shows, and the next hotkey prompts first. Unsaved captures live only in the open log, so locking is refused with an explanation while anything is pending or still being written, or while a passphrase change is rewriting the header, or a result that leaves the user unsure which passphrase now opens the log is still on screen: the "Passphrase changed" notice, or a failure during the write itself (those are the only place the user learns which passphrase the log now has, so a lock may not take them away). A refusal that changed nothing (a wrong current passphrase, an entry still pending, a new header that failed its check) holds no lock: that window is closed by the idle and workstation rules like any other dialog, and the outcome is in the diagnostics log. Every outcome of a change, never a passphrase, is written to the diagnostics log ([development.md](development.md)).
- Workstation lock: when Windows locks the session or signs the user out (`WM_WTSSESSION_CHANGE`), the log is locked the same way as by Lock now, since walking away is usually what locking the workstation means. The same refusals apply: if a capture is pending, a write is in flight or a passphrase change is under way at that moment, the lock is postponed and taken as soon as that work is done, as the idle check does. The session's locked state is tracked from the lock and unlock notifications (a sign-out locks the log but does not set that state, since it ends the process anyway): a postponed lock is cancelled when the session unlocks before it was taken, since the user is back and closing their typed text then would protect nothing; a log open that completes while the session is locked (the passphrase was entered just before the lock screen came up and the key was still deriving) locks at once rather than leaving the log open behind the lock screen until the idle limit; and if registering for the notifications fails at startup, it is retried once at the first unlock, and a balloon says the log will not follow the workstation lock if that fails too, since a silent failure here means the log stays open on an unattended machine.
- The passphrase is never written anywhere. The derived key is never written anywhere.
